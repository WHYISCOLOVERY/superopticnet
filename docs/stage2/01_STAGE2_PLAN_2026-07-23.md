# Stage 2 - Shared Design System Plan

Date: 2026-07-23

## Scope

Stage 2 is limited to the shared visual and interaction foundation:

- color, status, typography, spacing, radius and elevation tokens;
- button, form, card, table, filter, pagination, modal, drawer and badge
  components;
- loading, empty, error and confirmation states;
- shared toast and dirty-form behavior;
- accessible modal/drawer focus management;
- mobile and accessibility contract tests;
- additive pilot adoption without changing business services or workflows.

Module information architecture, duplicate route removal, Message Center
redesign and Agent Workspace remain later stages.

## Baseline

Captured before Stage 2 implementation:

- `css/portal.css`: `89204` bytes;
- `script/portal.js`: `29588` bytes;
- native `confirm()` calls: `6`;
- PHP lines containing inline `style` attributes or `<style>` blocks: `128`;
- shared mobile table labeling exists in `script/portal.js`;
- modal focus handling exists separately in Admin, Billing Customer and
  Operations Center pages;
- no shared toast or dirty-form runtime exists.

The existing 128 inline-style lines are technical debt. Stage 2 must not add
new inline styles. Removing all existing layout-specific inline styles in one
change is outside this phase because it would combine a design-system
foundation with a high-risk full product rewrite.

## Pilot Surfaces

The additive design-system state is enabled first on:

- `portal.php`: dashboard/card/button/state surface;
- `admin-users.php`: form, table, modal and destructive confirmation surface;
- `billing-customers.php`: filter, pagination and create modal surface;
- `operations-center.php`: Finance, HR and Inventory workbench surface.

Existing service calls, form actions, routes and DB behavior remain unchanged.

## Migration And Feature Flag

Migration `20260723_030_stage2_design_system` only seeds:

- `stage2_design_system`

The flag starts disabled. It controls pilot adoption through a body data
attribute. Static component assets are additive and safe to load while the
flag is disabled.

No business table or existing record is changed.

## Component Contract

### Tokens

- semantic surface, text, border and focus colors;
- success, warning, danger, info and neutral status colors;
- 4/8/12/16/24/32 spacing scale;
- 4/6/8 pixel radius scale;
- restrained elevation scale;
- fixed typography scale with zero letter spacing.

### Buttons And Forms

- primary, secondary, quiet and danger variants;
- small, medium and large sizes;
- minimum 44 pixel interactive target;
- visible focus, disabled and loading states;
- label, hint, validation and error associations.

### Containers And Data

- cards only for repeated records, modal/dialog content and framed tools;
- table wrapper with stable overflow and mobile labels;
- filter bar and active filter chips;
- deterministic 50-row pagination contract;
- no nested card requirement.

### Overlays

- modal and drawer use one focus trap;
- Escape and backdrop close only when allowed;
- opener focus is restored;
- page scroll is locked while open;
- `aria-modal`, title association and focus target are required.

### Feedback

- one toast host with polite/assertive live regions;
- success, warning, error and info variants;
- loading, empty and error components;
- destructive confirmation is an accessible application dialog, not native
  `confirm()`;
- dirty forms warn before internal navigation and browser unload.

## Tests

Required:

1. PHP and JS syntax/static contract.
2. Token and component marker coverage.
3. Native `confirm()` count equals zero.
4. No inline style is added by Stage 2 files or pilot changes.
5. Confirmation cancel/approve behavior.
6. Modal focus trap, Escape and opener-focus restoration.
7. Dirty-form clean, dirty, submit and navigation behavior.
8. Toast live-region and dismissal behavior.
9. Keyboard-only button/form/modal use.
10. Mobile overflow at `390x844`, `430x932` and `768x1024`.
11. Existing mobile, automatic filter, modal and full regression suites.

## Rollout

1. Apply migration with the flag disabled.
2. Load additive assets and run static/browser tests.
3. Enable the flag for pilot surfaces.
4. Run pilot screenshots and full regression.
5. Keep shared runtime active for explicit `data-ui-*` contracts only.
6. Later module adoption must reuse these components and may not introduce
   page-specific copies.

## Rollback

Operational rollback:

1. Disable `stage2_design_system`.
2. Pilot pages stop emitting the active design-system data attribute.
3. Existing page classes and workflows continue unchanged.

Schema rollback removes only the disabled flag row. No business data restore
is needed. The migration refuses to remove an enabled flag.

## Acceptance

Stage 2 is accepted only when:

- the shared component files and usage rules exist;
- pilot surfaces use the feature-gated foundation;
- native confirms are removed;
- toast and dirty-form behavior pass browser tests;
- accessibility and mobile contract tests pass;
- full regression has zero failures and timeouts;
- rollback disable and migration rollback/reapply are verified.
